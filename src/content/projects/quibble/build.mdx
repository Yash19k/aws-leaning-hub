In this guide you will read Quibble's code, run it on your laptop, deploy it to your own AWS account with one command, play a real game from your phone, and then host a quiz night for your club. Along the way you will see exactly how a stateless Lambda can run a live, 250-player game.

<Callout type="info" title="Coming from DropVault?">

You already met API Gateway (as a REST API), Lambda, S3 and DynamoDB in [DropVault](/projects/dropvault), which was built with Terraform. Quibble uses the same services in new ways and is deployed with [AWS SAM](/services/cloudformation). This guide links back to the basics instead of repeating them, and spends its time on what is new: WebSockets, pushing to browsers, timers without servers, and races between Lambdas.

</Callout>

## Part 3: Read the template, section by section

Everything Quibble creates in AWS is described in one file, `aws/template.yaml`. It is an AWS SAM template: CloudFormation plus shortcuts like `AWS::Serverless::Function`. You deployed a tiny one in [Your first deploy](/setup/first-sam-deploy). This one is bigger, so take it one section at a time.

<Step number={4} title="Parameters and Globals">

A <Term t="parameter">A value you pass in at deploy time, so the same template can be deployed with different settings.</Term> is a setting you can change without editing the template. These two matter most for a quiz night:

```yaml title="aws/template.yaml"
  MaxPlayers:
    Type: Number
    Default: 250
    MinValue: 1
    MaxValue: 1000
    Description: Most players one game accepts (load-tested at 250).
  LateGraceMs:
    Type: Number
    Default: 1500
    MinValue: 1
    MaxValue: 10000
    Description: >
      Answers that reached API Gateway up to this long after a question's timer hit zero still count.
      Raise it (e.g. 5000) while the account's Lambda concurrency quota is still low.
```

The others: `JwtSecret` (the key that signs login tokens; `NoEcho` hides it in the console and the deploy script generates it for you), `RevealMs` (the 4-second pause on each result), `LogRetentionDays` (14), `AlertEmail` and `AlertTimeZone` (for email alerts), and `ExtraCorsOrigin` (lets the local dev server call a deployed API).

`Globals` sets defaults for every function, so they are not repeated six times:

```yaml title="aws/template.yaml" {3-4,6}
Globals:
  Function:
    Runtime: nodejs22.x
    Architectures: [arm64]
    CodeUri: backend/
    MemorySize: 512 # more memory = more CPU: fan-out to 250 sockets and JSON work finish sooner
    Timeout: 15
    # No reserved concurrency anywhere: it carves slots out of the shared account pool (and is impossible while the
    # account quota is still the 10-slot default).
    Environment:
      Variables:
        USERS_TABLE: !Ref UsersTable
        # ... one variable per table ...
        WS_ENDPOINT: !Sub 'https://${WebSocketApi}.execute-api.${AWS::Region}.amazonaws.com/${WebSocketStageName}'
        # A plain name (not !Ref) so the timer function can reference itself without a circular dependency.
        TIMER_FUNCTION: !Sub '${AWS::StackName}-game-timer'
```

Why these choices:

- **arm64** (Graviton) costs less per second of compute than x86 TODO(verify), and nothing in Quibble needs x86.
- **512 MB:** in Lambda, more memory also means more CPU. Pushing a result to 250 sockets is lots of small network calls and JSON work, which finishes sooner with more CPU.
- **Table names come in as environment variables** (`!Ref UsersTable`), so the code never hard-codes a name. CloudFormation picks names like `quibble-UsersTable-1A2B3C`.
- **`WS_ENDPOINT`** is the address Lambdas call to push messages to browsers (Step 8 explains it).
- **`TIMER_FUNCTION`** is a plain string, not a `!Ref`. The game-timer invokes itself, and a function cannot `!Ref` itself without CloudFormation complaining about a circular dependency.

</Step>

<Step number={5} title="The nine DynamoDB tables">

All nine tables use `BillingMode: PAY_PER_REQUEST`, which DynamoDB calls <Term t="on-demand">You pay for each read and write instead of reserving capacity in advance. An idle table costs only its storage.</Term> mode.

| Table | What it holds | Hot during a game? |
|---|---|---|
| Games | One small header per game: status, current question, deadlines, `version` | Rarely written (phase changes only) |
| GamePlay | Everything many players write at once: seats, answers, question gates, scores | Yes |
| Connections | One item per open WebSocket | Yes (connects, disconnects) |
| Users | Accounts, `currentGame`, `sessionVersion` | Read on every message |
| Questions | The question bank | Read when a game is created |
| Results | Each player's game results, plus the leaderboards | Written when a game ends |
| Quizzes | Quizzes players build ("My quizzes") | No |
| RateLimits | Sign-up and failed-login counters | No |
| Admin | Audit log and the announcement banner | No |

Five tables (Users, Questions, Results, Quizzes, Admin) turn on point-in-time recovery, DynamoDB's continuous backup. Five use <Term t="TTL">Time to live: you store an expiry time on each item, and DynamoDB deletes the item for free some time after it passes.</Term> so old games, sockets and counters clean themselves up.

The two game tables are the interesting ones:

```yaml title="aws/template.yaml"
  # One small header item per game, written only when the game changes phase.
  GamesTable:
    Type: AWS::DynamoDB::Table
    Properties:
      BillingMode: PAY_PER_REQUEST
      AttributeDefinitions: [{ AttributeName: code, AttributeType: S }]
      KeySchema: [{ AttributeName: code, KeyType: HASH }]
      TimeToLiveSpecification: { AttributeName: expiresAt, Enabled: true }

  # Everything many players write at once (seats, answers, question gates, scores, results). Each item family has
  # its own partition key (<code>#P, <code>#A#<k>, <code>#Q ...) so no key takes more than one family's burst and
  # every key stays far below DynamoDB's per-partition limits. Items expire a day after the game.
  GamePlayTable:
    Type: AWS::DynamoDB::Table
    Properties:
      BillingMode: PAY_PER_REQUEST
      AttributeDefinitions:
        - { AttributeName: pk, AttributeType: S }
        - { AttributeName: sk, AttributeType: S }
      KeySchema:
        - { AttributeName: pk, KeyType: HASH }
        - { AttributeName: sk, KeyType: RANGE }
      TimeToLiveSpecification: { AttributeName: expiresAt, Enabled: true }
```

To see why GamePlay is designed this way, you need one idea. DynamoDB spreads items over storage partitions using each item's <Term t="partition key">The part of an item's key that decides which storage partition holds it. Items with the same partition key live together.</Term>. Each single key value can take only so much traffic: the README works with about 1,000 writes and 3,000 reads per second. If all 250 answers updated one big "game" item, that one key would get the whole burst, a so-called hot key.

Think of a supermarket with one checkout counter versus ten. Quibble opens a separate counter for each kind of item. Here are the real keys from `lib/gamedata.js`, for a game with code `K7M2QX`:

| Partition key | Sort key | Holds | Written at once by |
|---|---|---|---|
| `K7M2QX#M` | `Q` | The game's questions (never change) | Nobody after creation |
| `K7M2QX#L` | `L` | Lobby gate: open flag, seat counter, player limit | Everyone joining |
| `K7M2QX#P0` to `K7M2QX#P3` | user id | One member item per player: seat and open sockets (`conns`) | Sockets attaching, spread over 4 keys |
| `K7M2QX#Q` | question index | One gate per question: deadline, answered count, seats that answered | Everyone answering |
| `K7M2QX#A#3` | seat | One item per answer to question 3 | Everyone answering, one item each |
| `K7M2QX#S` | `S` | Running scores | The closer, once per question |
| `K7M2QX#R` | question index | Each question's result | The closer |
| `K7M2QX#B` | `B` | Claims: a pending lobby push, the un-stick lease | Rarely |
| `K7M2QX#E0` to `K7M2QX#E3` | `E` | Emoji reaction counters | Everyone reacting, spread over 4 keys |

And the Games header is the opposite: one small item that changes only when the game moves to a new phase. That split, **state divided by who writes it**, is the core design idea of the whole project.

</Step>

<Step number={6} title="The website bucket">

```yaml title="aws/template.yaml" {12,23-24}
  FrontendBucket:
    Type: AWS::S3::Bucket
    Properties:
      WebsiteConfiguration:
        IndexDocument: index.html
        ErrorDocument: index.html
      OwnershipControls:
        Rules: [{ ObjectOwnership: BucketOwnerEnforced }]
      PublicAccessBlockConfiguration:
        BlockPublicAcls: true
        IgnorePublicAcls: true
        BlockPublicPolicy: false # the bucket policy below makes objects publicly readable
        RestrictPublicBuckets: false

  FrontendBucketPolicy:
    Type: AWS::S3::BucketPolicy
    Properties:
      Bucket: !Ref FrontendBucket
      PolicyDocument:
        Statement:
          - Sid: PublicReadForWebsite
            Effect: Allow
            Principal: '*'
            Action: s3:GetObject
            Resource: !Sub '${FrontendBucket.Arn}/*'
```

In DropVault the bucket was private and every download needed a presigned link. Here the bucket is **public on purpose**: it only holds the website's HTML, CSS and JavaScript, which every player's browser must download anyway. The bucket policy allows anyone to `GetObject` (read files) and nothing else. Old-style ACLs stay blocked; only the policy grants access.

Players use the bucket's HTTPS address, `https://<bucket>.s3.<region>.amazonaws.com/index.html` (the `WebsiteUrl` output). S3's "static website" address also exists, but it is plain HTTP and browsers warn about it. The HTTPS address has no index page, so links always name a file, such as `/play.html?code=K7M2QX`.

<Callout type="security" title="Nothing secret in this bucket">

Everything in it is public. The only generated file, `config.js`, contains just the two API URLs. Passwords and the JWT secret never come near it.

</Callout>

</Step>

<Step number={7} title="The HTTP API (the familiar part)">

This is the request-and-response side: sign-up, login, leaderboards, match history, My quizzes and the admin console. DropVault used API Gateway's REST API type; this is the HTTP API type, a lighter and cheaper flavour with fewer features TODO(verify).

```yaml title="aws/template.yaml"
  HttpApi:
    Type: AWS::Serverless::HttpApi
    Properties:
      CorsConfiguration:
        AllowOrigins:
          - !Sub 'https://${FrontendBucket.RegionalDomainName}' # the HTTPS page players open
          - !GetAtt FrontendBucket.WebsiteURL # the old HTTP website endpoint
          - !Ref ExtraCorsOrigin
        AllowHeaders: [content-type, authorization]
        AllowMethods: [GET, POST, PUT, PATCH, DELETE, OPTIONS]
        ExposeHeaders: [retry-after] # the page honours Retry-After when it backs off
        MaxAge: 600
      # Whole-API ceiling (the account allows 10,000 rps shared by every API). 200 sign-ups at once is far below.
      DefaultRouteSettings:
        ThrottlingBurstLimit: 2000
        ThrottlingRateLimit: 1000
```

<Term t="CORS">Cross-Origin Resource Sharing: browser rules that block a page on one address from calling an API on another, unless the API says that page is allowed.</Term> matters because the page lives on `s3.amazonaws.com` and the API on `execute-api.amazonaws.com`. The API lists exactly which pages may call it.

The function side uses a single catch-all route:

```yaml title="aws/template.yaml"
      Events:
        Api:
          Type: HttpApi
          Properties:
            ApiId: !Ref HttpApi
            Path: /api/{proxy+}
            Method: ANY
```

Every `/api/...` request goes to one Lambda (`handlers/http.js`), which matches the path against its own list of routes. One function keeps cold starts and deploys simple for a small API.

</Step>

<Step number={8} title="The WebSocket API (the new part)">

This is where Quibble stops looking like DropVault.

**A normal HTTP request is like sending a letter.** The browser asks, the server answers, and the conversation is over. The server can never start a conversation; if something changes, it has to wait until the browser asks again.

**A WebSocket is like a phone call.** The browser makes one special HTTP request (a handshake that asks to "upgrade" the connection), and from then on the connection stays open. Either side can send a message, called a frame, at any moment. That is exactly what a quiz needs: the server must tell 250 phones "time's up" the instant it happens.

You do not run a server to hold those open connections. **API Gateway holds them for you**, and calls your Lambda functions only when something happens. It calls them through three special routes:

| Route | When API Gateway uses it | Quibble's Lambda | What it does |
|---|---|---|---|
| `$connect` | During the handshake, before the socket is accepted | ws-connect | Checks the login token; a 401 refuses the connection |
| `$default` | For any frame that matches no other route | ws-message | Every game action: join, start, answer, react, sync |
| `$disconnect` | After a socket closes, on a best-effort basis | ws-disconnect | Marks the player offline |

```yaml title="aws/template.yaml" {6,18}
  WebSocketApi:
    Type: AWS::ApiGatewayV2::Api
    Properties:
      Name: !Sub '${AWS::StackName}-ws'
      ProtocolType: WEBSOCKET
      RouteSelectionExpression: '$request.body.action'

  ConnectIntegration:
    Type: AWS::ApiGatewayV2::Integration
    Properties:
      ApiId: !Ref WebSocketApi
      IntegrationType: AWS_PROXY
      IntegrationUri: !Sub 'arn:aws:apigateway:${AWS::Region}:lambda:path/2015-03-31/functions/${WsConnectFunction.Arn}/invocations'
  ConnectRoute:
    Type: AWS::ApiGatewayV2::Route
    Properties:
      ApiId: !Ref WebSocketApi
      RouteKey: $connect
      AuthorizationType: NONE # the Lambda checks the JWT itself
      Target: !Sub 'integrations/${ConnectIntegration}'
```

The `$disconnect` and `$default` routes follow the same pattern. `RouteSelectionExpression` tells API Gateway to read the `action` field of each JSON frame to pick a route. Quibble's browser sends every frame like this (from `public/js/realtime.js`):

```javascript title="public/js/realtime.js"
        frame: JSON.stringify({ action: 'message', id, event, data }),
```

There is no route called `message`, so every frame falls through to `$default`, and ws-message reads the `event` field (`room:join`, `answer:submit` ...) itself. The stage adds a throttle with plenty of headroom, because 250 players answering within the same 100 ms is a 250-message burst:

```yaml title="aws/template.yaml"
  WebSocketStage:
    Type: AWS::ApiGatewayV2::Stage
    Properties:
      ApiId: !Ref WebSocketApi
      StageName: !Ref WebSocketStageName
      DeploymentId: !Ref WebSocketDeployment
      # 250 players answering within the same 100 ms is a 250-message burst; leave plenty of headroom.
      DefaultRouteSettings:
        ThrottlingBurstLimit: 2000
        ThrottlingRateLimit: 1000
```

Each of the three functions also gets an `AWS::Lambda::Permission`, which allows API Gateway (`apigateway.amazonaws.com`) to invoke it.

**Talking back.** A Lambda never holds a socket. When it wants to send something to a browser, it calls API Gateway's **Management API** at the `WS_ENDPOINT` address from Step 4, using the action `PostToConnection` with the socket's connection id. API Gateway delivers the message down that open connection. To broadcast a question, a Lambda makes one `PostToConnection` call per player socket, all in parallel. You can see the code in the "Pushing to every socket" code peek on the project page.

<Callout type="warning" title="Why connections are harder than requests">

- **Connections drop.** Phones switch networks and tabs sleep. A socket can die silently.
- **`$disconnect` is best effort.** AWS tries to tell you a socket closed, but the call can be late or never arrive, so nothing may depend on it.
- **Idle and maximum time.** API Gateway closes a socket after 10 minutes of silence and after 2 hours in total (README). `realtime.js` pings every 5 minutes and simply reconnects after the 2-hour cut.
- **Reconnects get a new id.** The same player comes back with a different connection id, so the server must re-attach it to the game.
- **Pushes can arrive late or twice.** Every push carries the game's `version` (`v`), and the browser ignores anything older than what it already shows.

</Callout>

<Step number={9} title="The functions and their permissions">

| Function | Handler | Started by | Memory, timeout |
|---|---|---|---|
| api | `handlers/http.js` | HTTP API (`/api/*`) | 1,769 MB, 20 s |
| ws-connect | `handlers/wsConnect.js` | `$connect` | 512 MB, 15 s |
| ws-message | `handlers/wsMessage.js` | `$default` | 512 MB, 15 s |
| ws-disconnect | `handlers/wsDisconnect.js` | `$disconnect` | 512 MB, 15 s |
| game-timer | `handlers/gameTimer.js` | Async invoke from the other functions (and itself) | 512 MB, 120 s |
| monitor | `handlers/monitor.js` | EventBridge schedule and rule, CloudWatch alarms | 256 MB, 60 s |

The api function gets 1,769 MB because bcrypt password hashing is CPU-heavy and a whole classroom may sign up at once. Here is ws-message:

```yaml title="aws/template.yaml"
  WsMessageFunction:
    Type: AWS::Serverless::Function
    Properties:
      Description: WebSocket $default - game actions (create, join, start, answer...)
      Handler: src/handlers/wsMessage.handler
      LoggingConfig: { LogGroup: !Ref WsLogGroup }
      Policies:
        - DynamoDBCrudPolicy: { TableName: !Ref UsersTable } # creating a game is one transaction with the user item
        - DynamoDBReadPolicy: { TableName: !Ref QuestionsTable }
        - DynamoDBReadPolicy: { TableName: !Ref QuizzesTable } # hosting one of My quizzes
        - DynamoDBCrudPolicy: { TableName: !Ref GamesTable }
        - DynamoDBCrudPolicy: { TableName: !Ref GamePlayTable }
        - DynamoDBCrudPolicy: { TableName: !Ref ConnectionsTable }
        - DynamoDBCrudPolicy: { TableName: !Ref ResultsTable }
        - Statement:
            - Effect: Allow
              Action: execute-api:ManageConnections
              Resource: !Sub 'arn:aws:execute-api:${AWS::Region}:${AWS::AccountId}:${WebSocketApi}/${WebSocketStageName}/*/@connections/*'
            - Effect: Allow
              Action: lambda:InvokeFunction
              Resource: !Sub 'arn:aws:lambda:${AWS::Region}:${AWS::AccountId}:function:${AWS::StackName}-game-timer'
```

SAM turns each `Policies` list into an <Term t="IAM role">An identity with a set of permissions that an AWS service (here, a Lambda function) takes on while it runs.</Term> for that one function. `DynamoDBReadPolicy` and `DynamoDBCrudPolicy` are SAM shortcuts for "read" and "read and write" on one table. The two custom statements are the real-time ones: `execute-api:ManageConnections` lets this function push to sockets of this API's stage only, and `lambda:InvokeFunction` lets it start the game-timer and no other function. ws-connect, by contrast, can only read Users and write Connections.

The game-timer has a few special settings:

```yaml title="aws/template.yaml"
  GameTimerFunction:
    Type: AWS::Serverless::Function
    Properties:
      FunctionName: !Sub '${AWS::StackName}-game-timer'
      Description: Waits for a question/reveal deadline, then advances the game
      Handler: src/handlers/gameTimer.handler
      MemorySize: 512 # pushes each question and result to every player
      Timeout: 120
      # Each timer schedules the next one (question -> reveal -> question ...). Without this, Lambda's recursive-loop
      # detection stops the chain after ~16 hops, i.e. in the middle of a game.
      RecursiveLoop: Allow
      LoggingConfig: { LogGroup: !Ref TimerLogGroup }
      EventInvokeConfig:
        MaximumRetryAttempts: 2 # every step is idempotent, so a retry is safe
        MaximumEventAgeInSeconds: 600 # throttled events wait in Lambda's queue (with backoff) this long
```

- **A fixed `FunctionName`** lets the other functions (and the timer itself) find it by name.
- **`Timeout: 120`**, because the timer stays awake for a whole question, which can be 20 or 25 seconds plus the grace period.
- **`RecursiveLoop: Allow`**, because the timer keeps scheduling itself, and Lambda's loop detection would otherwise stop it mid-game.
- **`EventInvokeConfig`**: if a timer run fails, Lambda retries it twice; if Lambda is busy, the event waits in a queue for up to 10 minutes instead of being dropped.

</Step>

<Step number={10} title="Monitoring and email alerts">

The template also builds its own monitoring. Every function logs one JSON object per line into a log group kept for 14 days. Custom game metrics (games started, answers submitted ...) use CloudWatch's <Term t="Embedded Metric Format">A specially shaped log line that CloudWatch turns into a real metric, with no extra API calls or permissions.</Term>, written by `lib/log.js`.

There are 14 alarms. Here is one:

```yaml title="aws/template.yaml"
  LambdaThrottlesAlarm:
    Type: AWS::CloudWatch::Alarm
    Properties:
      AlarmName: !Sub '${AWS::StackName}-lambda-throttles'
      AlarmDescription: Lambda throttled invocations in this account and region (concurrency quota reached)
      Namespace: AWS/Lambda
      MetricName: Throttles
      Statistic: Sum
      Period: 60
      EvaluationPeriods: 1
      Threshold: 1
      ComparisonOperator: GreaterThanOrEqualToThreshold
      TreatMissingData: notBreaching
```

## Part 4: Walk through the Lambda code

Each handler is short. The real work lives in `aws/backend/src/lib/`, mostly in `game.js`.

<Step number={12} title="ws-connect: who gets a socket">

**Receives:** the `$connect` event, with the socket's `connectionId` and the `?token=` query string. **Returns:** `200` to accept the socket or `401` to refuse it.

```javascript title="aws/backend/src/handlers/wsConnect.js"
export const handler = async (event) => {
  const claims = verifyToken(event.queryStringParameters?.token);
  // Strongly consistent: the browser opens its socket right after signing up.
  const user = claims && (await getUserById(claims.userId, { consistent: true }));
  if (!user || user.banned || tokenRevoked(user, claims.sv)) return { statusCode: 401, body: 'unauthorized' };
  // tokenIat lets `hello` hand out a fresh token before a long event outlives the old one; tokenSv lets every message
  // check the socket's token wasn't signed out since.
  await saveConnection(event.requestContext.connectionId, user.id, claims.iat, claims.sv);
  log('info', 'socket connected', { userId: user.id, connectionId: event.requestContext.connectionId });
  return { statusCode: 200, body: 'ok' };
};
```

Step by step:

1. `verifyToken` checks the <Term t="JWT">JSON Web Token: a small signed string that says who you are. The server can check the signature without a database lookup.</Term> signature with the secret, without touching the database. The token is in the URL because the browser's WebSocket API cannot add an `Authorization` header.
2. It reads the user with a **strongly consistent** read. DynamoDB reads are normally "eventually consistent" and may miss a write from a moment ago; the player may have signed up one second earlier.
3. Banned, deleted, or signed out by an admin ("sign out everywhere" bumps a `sessionVersion` that `tokenRevoked` compares): `401`, and API Gateway refuses the socket.
4. Otherwise it saves a Connections item (with a 3-hour TTL, since API Gateway closes sockets after 2 hours anyway).

</Step>

<Step number={13} title="ws-message: one door for every game action">

**Receives:** a `$default` event whose `body` is a frame like `{"action":"message","id":"9f2c41ab-4","event":"room:join","data":{"code":"K7M2QX"}}`. **Returns:** always `200` to API Gateway; the real reply is an **ack** pushed back to the socket.

```javascript title="aws/backend/src/handlers/wsMessage.js"
const actions = {
  hello: game.hello,
  sync: game.hello,
  ping: () => ({ serverNow: Date.now() }),
  'game:create': game.create,
  'room:join': game.join,
  'game:start': game.start,
  'game:cancel': game.cancelByHost,
  'room:leave': game.leave,
  'answer:submit': game.submitAnswer,
  react: game.react,
};
```

For each frame it:

1. Looks up the action (own properties only, so a frame cannot name `constructor` or `__proto__`).
2. Reads the socket's Connections item and the user, both strongly consistent, on **every** message, so a ban applies instantly.
3. Validates `data` against a schema (`lib/schemas.js`, using zod).
4. Builds a context with the time the frame **reached API Gateway**:

```javascript title="aws/backend/src/handlers/wsMessage.js"
      // When API Gateway received this frame: answer deadlines and speed points use it, so a cold start or a
      // throttled-and-resent message never costs the player.
      now: Number(event.requestContext.requestTimeEpoch) || Date.now(),
```

5. Runs the action and pushes `{ type: 'ack', id, ok: true, ... }` back with the same `id`.
6. Runs "deferred" work after the ack, such as closing a question early or asking for a lobby push, so the player is never kept waiting for it.

Because the browser resends any frame that was not acknowledged, **every action must be <Term t="idempotent">Safe to repeat: doing it twice has the same effect as doing it once.</Term>**. Joining twice keeps one seat; answering twice keeps the first answer. If something temporary fails (throttling, a timeout), the ack says `retry: true` and the browser tries again after a short, random pause.

</Step>

<Step number={14} title="The game engine: state, answers and phase changes">

`lib/game.js` is a state machine: `lobby`, then `question` and `reveal` for each question, then `ended`. Three rules keep it consistent without a server.

**1. Hot paths never rewrite shared state.** A join is one atomic counter on the lobby gate plus one new member item. An answer is one new item plus one atomic update of the question's gate. See the code peek **"An answer is two conditional writes"** on the project page: a <Term t="conditional write">A DynamoDB write that only happens if a condition on the item is true, checked atomically by DynamoDB itself.</Term> stores the answer only if it does not exist yet, and another adds the seat to the gate only while the question is open.

**2. Phase changes are transactions guarded by `version`.** Opening a question, showing its result and ending the game each happen in one DynamoDB transaction (several writes that all succeed or all fail), on the condition that the Games header still has the `version` this Lambda read. When several Lambdas try the same step, exactly one wins. See the code peek **"Exactly one Lambda wins a phase change"**.

**3. Whoever wins a phase change starts the next timer first, then tells everyone.** Here is the end of `openQuestion`:

```javascript title="aws/backend/src/lib/game.js"
  if (!(await commit(items))) return false;

  const h = { ...header, ...fields, version: header.version + 1 };
  await scheduleOrLog({ kind: 'question', code, qIndex: k, dueAt: acceptUntil }); // before the push: a timer must exist
  metric('QuestionsAsked');
  await broadcast(h, await gd.queryMembers(code), 'question:show', () => V.questionShow(h, q, { k, endsAt, acceptUntil }, Date.now()));
  return true;
```

If `commit` returns `false`, someone else already opened this question, and this Lambda quietly stops. Otherwise it schedules the timer before the push, so a question on screen always has a clock behind it. `broadcast` reads every member item's `conns` (the open socket ids) and pushes to all of them.

Two smaller tricks keep a full room cheap. Lobby lists are pushed at most once every 500 ms (`BROADCAST_WINDOW_MS`), no matter how many people join in that window. Emoji reactions are counted on 4 shard items and pushed about once a second.

</Step>

<Step number={15} title="game-timer: a clock made of Lambdas">

In a normal Node.js server you would write `setTimeout(closeQuestion, 15000)`. In Lambda that does not work: once a function returns, its environment can be frozen or thrown away, so the timer would never reliably fire. And the game cannot live in memory either, because the next event may run on a completely different copy of the function.

Quibble's answer: when a phase begins, the winner **invokes the game-timer function asynchronously** with the deadline. "Asynchronously" (`InvocationType: 'Event'`) means Lambda puts the event in a queue and the caller moves on at once. The handler accepts five kinds of events:

```javascript title="aws/backend/src/handlers/gameTimer.js"
// GameTimer: invoked asynchronously (fire-and-forget) with one of
//   {kind:'question', code, qIndex, dueAt}  pushes answer counts, then closes the question at its deadline
//   {kind:'reveal',   code, qIndex, dueAt}  opens the next question (or ends the game) after the reveal pause
//   {kind:'lobby',    code, due, dueAt}     pushes the batched lobby list
//   {kind:'unstick',  code}                 moves an overdue game on (its timer was lost)
// Every kind is idempotent, so Lambda's automatic retries, duplicates and late deliveries are harmless.
```

(The code also handles a fifth kind, `reactions`, for emoji.) The question timer stays awake for the whole question:

```javascript title="aws/backend/src/lib/game.js"
/** Lives for the whole question: pushes answer counts, then closes the question at its deadline. */
async function questionTimer({ code, qIndex: k, dueAt }) {
  let lastCount = 0;
  // ...
  while (Date.now() < dueAt) {
    await sleep(Math.min(COUNT_POLL_MS, Math.max(0, dueAt - Date.now())));
    if (Date.now() >= dueAt) break;
    // Cheap eventually consistent poll; a miss is re-checked strongly (a lagging replica must not kill the closer).
    const gate = (await gd.getGate(code, k, { consistent: false })) ?? (await gd.getGate(code, k));
    if (!gate) return;
    // ... (if someone else is already closing it, wait or take over)
    if (gate.answered !== lastCount) {
      // ...
      lastCount = gate.answered;
      await broadcast(header, members, 'answer:count', () => V.answerCount(header, k, gate.answered));
    }
  }
  // The deadline: this timer is the guaranteed closer. If someone else claimed the close and is still working (or
  // died), keep checking until the question is really closed; closeQuestion takes over once their claim is stale.
  const giveUpAt = Date.now() + TAKEOVER_MS + 3000;
  while (!(await closeQuestion(code, k)) && Date.now() < giveUpAt) {
    if (!V.isQuestionAt(await gd.getHeader(code), k)) return;
    await sleep(1000);
  }
}
```

So the chain for one question is: the question timer pushes live counts, then calls `closeQuestion` at the deadline. `closeQuestion` scores the answers, commits the `reveal` phase and schedules a **reveal** timer. The reveal timer sleeps 4 seconds and opens the next question, which schedules the next question timer. That is why the function calls itself, and why it needs `RecursiveLoop: Allow`.

The deadline is `acceptUntil`, which is the visible end of the countdown plus `LateGraceMs`. An answer that reached API Gateway in that grace window still counts.

**What if a timer gets lost?** Lambda retries failed async events twice. If one is lost for good, players' browsers notice: when a phase is 4 seconds overdue, each browser's watchdog starts sending `sync` (the same as `hello`). Once the game is clearly overdue (8 seconds past its deadline), the server schedules one `unstick` run under a 10-second lease, so 250 browsers cause only one.

<Callout type="cost" title="The timer is billed while it sleeps">

Lambda bills for the time a function runs, including time spent in `sleep`. A 15-second question keeps one 512 MB timer running for about 16.5 seconds. That is still tiny for a club game, but it is the price of not running a server.

</Callout>

  options={["setTimeout is not available in Node.js 22", "The Lambda environment can be frozen or discarded after it returns, so the timer may never fire", "DynamoDB does not allow writes from timers", "API Gateway blocks timers"]}

<Step number={16} title="ws-disconnect: cleaning up, best effort">

**Receives:** the `$disconnect` event with the closed socket's `connectionId`. **Returns:** `200` (API Gateway ignores the answer).

```javascript title="aws/backend/src/lib/game.js"
/** $disconnect: forget the socket; if it was the member's last one they are now offline. */
export async function disconnect(connectionId) {
  const conn = await deleteConnectionRecord(connectionId);
  if (!conn?.gameCode) return;
  const r = await removeConn(conn.gameCode, conn.userId, connectionId);
  if (r?.wentOffline) await onOffline(conn.gameCode, r.member);
}
```

It deletes the Connections item, removes the socket from the member's `conns` set, and if that was the player's last tab, lowers the question gate's `expected` count, so a question can close early without waiting for someone who left. If that leaves everyone else answered, ws-disconnect may close the question itself, which is why it also has permission to push and to invoke the timer.

Because `$disconnect` may never arrive, nothing depends on it. A push to a dead socket fails with `GoneException`, and the broadcaster cleans that socket up on the spot. Closing early always double-checks who is really connected. And the TTL on Connections removes leftovers after 3 hours.

</Step>

## Part 9: Run it in your club meeting

You have a working, monitored, 250-player quiz. Here is how to run a real event with it, based on the README's "Before an event" checklist.

<Step number={29} title="A week before">

- **Quota is 1,000.** Run `npm run quota:lambda`. If it is still 10, request it now with `npm run quota:lambda -- --request`; approval can take a while.
- **SAM CLI is 1.123 or newer.** Run `sam --version`.
- **Preflight passes.** Run `npm run preflight`. Use `-- --allow-degraded` only if you accept slower phases on a low quota.
- **Latest version deployed.** Run `npm run deploy`, and add `-- LateGraceMs=5000` if the quota is still low.
- **Email alerts on** (Step 24), so you hear about problems before the audience does.
- **Your questions are ready.** Use the built-in bank, import questions in the admin console, or build your own quiz under **My quizzes** (players never see the answers).
- **Rehearse** a short game with three or four friends on their own phones and mobile data.

</Step>

<Step number={30} title="On the day">

- **Share the HTTPS link.** Put the `WebsiteUrl` (`https://...amazonaws.com/index.html`) on a slide, or let people scan the lobby's QR code (`.../play.html?code=K7M2QX`). Avoid the plain-HTTP address: browsers warn about it.
- **Let people sign up first.** Open the link a few minutes early so everyone has an account before you start. The limits are sized for a classroom on one Wi-Fi: 500 sign-ups per IP address per hour and 200 failed logins per IP per 15 minutes.
- **Open the lobby early.** A lobby stays open for 3 hours, so you can create the game before people arrive.
- **Use Big-screen mode** on the projector: the laptop becomes the room's display (big question, timer, animated leaderboard) and phones become answer pads. If you want to play too, join from your phone.
- **Keep the CloudWatch dashboard open** on a second tab: Lambda concurrency and throttles, DynamoDB throttles.
- **No deploys while a game is running.** The preflight warns about live games for a reason.
- **If something looks stuck,** wait a few seconds: phones resync by themselves. As a last resort, the admin console's **Live games** page can end any game for everyone.
- **Afterwards**, the leaderboards (all time and this week) and each player's match history are already there.

</Step>

## Part 10: Challenges

<Step number={31} title="Pick a challenge">

Each of these is a real improvement, and several come straight from the README's "Known trade-offs".

1. **Put [CloudFront](/services/cloudfront) in front of the bucket.** Get a custom domain and clean `/` URLs instead of `.../index.html`. Hint: you can then make the bucket private and let only CloudFront read it.
2. **Move the JWT secret out of environment variables** into SSM Parameter Store or Secrets Manager, and read it once per Lambda container.
3. **Keep leaderboards up to date with DynamoDB Streams** instead of scanning the Results table after every game.
4. **Add a team mode.** Players join a team, and the result shows team totals. Decide first: which new partition keys do you need so that 250 answers still never hit one key?
5. **Break it on purpose, locally.** Run `npm run dev` with `LOCAL_LAMBDA_CONCURRENCY=10 LOCAL_TRACK_CAPACITY=1`, then `npm run test:load -- --players 200 --questions 12 --spread 0 --drop 15`, and read `http://localhost:5050/__local/capacity` to see the busiest partition keys.
6. **Add a question type.** Look at `lib/qtypes.js` (how answers are checked) and `lib/views.js` (what is sent before and after the reveal), and make sure the answer never leaks early.

</Step>
