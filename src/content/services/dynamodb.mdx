DynamoDB is a **NoSQL** database: there are no SQL joins and no fixed columns. You store **items** (think JSON objects) in **tables**, and every item has a **key**. Ask for an item by its key and DynamoDB returns it in milliseconds, whether the table holds a hundred items or a billion.

The trade-off is that you design the table around the questions your app will ask ("all files of this user", "all answers to question 3"), not around a tidy diagram of entities. Get that right and you never need a server or a connection pool.

## Key ideas

<KeyConcepts>
  <Concept title="Table, item and attributes">A table holds items. Each item is a set of attributes (name and value pairs). Items in the same table can have different attributes, which lets one table hold several kinds of record.</Concept>
  <Concept title="Partition key and sort key">The **partition key** decides where an item is stored and is what you look it up by. An optional **sort key** lets many items share a partition key and come back in order, like all answers for one question.</Concept>
  <Concept title="Query vs Scan">A **Query** reads only the items under one partition key: fast and cheap. A **Scan** reads the whole table: fine for an admin page, slow and costly for everyday requests.</Concept>
  <Concept title="Global secondary index (GSI)">A second copy of the table, keyed differently, so you can query by another attribute. An index is **sparse** when only some items have its key attribute: the others simply don't appear in it.</Concept>
  <Concept title="TTL and streams">**TTL** (time to live) deletes an item after the Unix timestamp in an attribute you choose. Deletion is not instant: it can take a while after the time passes TODO(verify). A **stream** is a log of every change to the table that a Lambda can react to.</Concept>
  <Concept title="Conditional writes and transactions">A **condition** makes a write happen only if something is true, like 'only if this item doesn't exist yet'. A **transaction** groups several writes so they all succeed or all fail. Both stop two requests from stepping on each other.</Concept>
</KeyConcepts>

## How our projects use it

### DropVault

[DropVault](/projects/dropvault) has a users table (`enclave-users-dev`, keyed by `email`) and one main files table (`enclave-files-dev`, keyed by `file_id`). Both use **on-demand** billing.

- **Several kinds of item in one table.** A key like a UUID is a file, `QR#<code>` is a short link, `USAGE#<user_id>` is a storage counter, `USERKEY#<user_id>` records a per-user KMS key, and `AUDIT#...` is an admin log entry.
- **Two sparse GSIs.** `user-files` (user to files, newest first) only contains file items, because only they have `user_id`. `file-links` (file to links) only contains links. So listing your files is a Query, never a Scan.
- **TTL plus a stream.** New uploads carry a `ttl` one day out. If the upload never finishes, TTL deletes the record, the stream (set to show the old item) passes the deletion to the `cleanup` Lambda, and it removes the partial file from S3.
- **Conditional updates.** A download only counts if `downloads < :max`, so two people can't both grab the last download of a limited link. The quota check-and-add on upload is also one conditional update.

### Quibble

[Quibble](/projects/quibble) uses nine on-demand tables, including Users, Questions, Games, GamePlay, Connections, Results and Quizzes.

- **Split by who writes.** `GamesTable` holds one small header per game that changes only between phases. Everything 250 players write at once goes to `GamePlayTable`, where each kind of item gets its own partition key (`<code>#A#<k>` for answers to question k, `<code>#S` for scores...), so no single key takes the whole burst.
- **Conditional writes for answers.** An answer is stored with `attribute_not_exists(#sk)`, so a resent message keeps its first arrival time. Then the seat is added to the question's gate only while the question is still open.
- **Transactions for phase changes.** Moving to the next question is a `TransactWriteCommand` guarded by the header's `version` number. If several Lambdas try the same step, exactly one wins.
- **TTL everywhere it helps.** Games, game-play items, sockets, rate-limit counters and year-old audit entries all expire through an `expiresAt` attribute. The tables you'd hate to lose (Users, Questions, Results, Quizzes, Admin) have point-in-time recovery switched on.

## Free Tier and cost

<Callout type="cost" title="How DynamoDB is billed">

**On-demand** tables (what both projects use) charge per read request and per write request, plus storage per GB-month. **Provisioned** tables charge per hour for capacity you reserve. Streams, backups and point-in-time recovery are billed extra TODO(verify).

- DynamoDB has had an always-free allowance that includes 25 GB of storage TODO(verify). Check which parts apply to on-demand tables TODO(verify).
- A Scan reads, and bills, every item it touches. That's one reason both projects avoid scans on everyday requests.
- Items deleted by TTL don't cost a write TODO(verify).

AWS changed the Free Tier for new accounts in 2025 to a credits-based free plan TODO(verify). See [Create your AWS account](/setup/create-aws-account).
