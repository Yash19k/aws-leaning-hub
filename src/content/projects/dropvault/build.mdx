## Part 2: The infrastructure, file by file

Everything in AWS is described in the `terraform/` folder. You won't type any of this, but reading it is the best way to understand what you are about to create.

<Step number={3} title="How the Terraform is organised">

Terraform is <Term t="infrastructure as code">Describing your servers, databases and permissions in text files, so a tool can create them the same way every time, and you can review changes like code.</Term>. You write *what should exist*; Terraform works out *what to create, change or delete* to get there.

Three ideas carry you through every file:

- A **provider** is a plugin that talks to one platform. `versions.tf` asks for the AWS provider (plus small helpers: `random` for a secret, `archive` to zip code, `null` to run a script).
- A **resource** block is one thing to create, like `resource "aws_s3_bucket" "files"`. The first label is the type, the second is a name you use to refer to it elsewhere (`aws_s3_bucket.files.arn`).
- The **state file** (`terraform.tfstate`) is Terraform's memory of what it created. Never delete it while the resources exist, or Terraform forgets they are there.

```hcl title="terraform/versions.tf"
terraform {
  required_version = ">= 1.5"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
    ...
  }
  # Local state by default. To use a remote S3 backend, add a backend "s3" block.
}

provider "aws" {
  region  = var.aws_region
  profile = var.aws_profile != "" ? var.aws_profile : null
}
```

`variables.tf` declares every setting (`aws_region`, `sender_email`, `web_hosting`...) with a default where it makes sense. You will fill them in a file called `terraform.tfvars` in Step 16.

`locals.tf` builds the names everything shares. Notice the prefix: it is `app_name` + `environment`, which default to `enclave` and `dev`. That is why your AWS resources will be called `enclave-dev-...` even though the app shows the name DropVault (a separate setting, `display_name`).

```hcl title="terraform/locals.tf" {3}
locals {
  account_id        = data.aws_caller_identity.current.account_id
  prefix            = "${var.app_name}-${var.environment}"
  table_name        = var.table_name != "" ? var.table_name : "${var.app_name}-files-${var.environment}"
  files_bucket_name = var.files_bucket_name != "" ? var.files_bucket_name : "${local.prefix}-files-${local.account_id}"

  functions = {
    create-upload = { dir = "upload-file", module = "upload_file", layers = ["jsonschema"] }
    complete      = { dir = "complete-upload", module = "complete_upload", layers = [] }
    download      = { dir = "download-file", module = "download_file", layers = [] }
    list          = { dir = "get-user-files", module = "get_user_files", layers = [] }
    delete        = { dir = "delete-user-file", module = "delete_user_file", layers = [] }
    share         = { dir = "share-file", module = "share_file", layers = ["jsonschema"] }
    cleanup       = { dir = "cleanup", module = "cleanup", layers = [] }
  }
  ...
}
```

The bucket name ends with your account ID because S3 bucket names must be unique across all of AWS. The `functions` map is a list of seven Lambdas that are built the same way; Step 5 shows how one resource block creates all seven.

</Step>

<Step number={4} title="Storage: s3.tf and dynamodb.tf">

**The files bucket (`s3.tf`)** is locked down in four ways: a public access block (nothing can ever be made public), owner-enforced object ownership, default encryption, and a bucket policy that refuses anything not sent over HTTPS. Two rules make it usable:

```hcl title="terraform/s3.tf"
resource "aws_s3_bucket_lifecycle_configuration" "files" {
  bucket = aws_s3_bucket.files.id
  rule {
    id     = "abort-incomplete-multipart-uploads"
    status = "Enabled"
    filter {}
    abort_incomplete_multipart_upload { days_after_initiation = 1 }
  }
}

resource "aws_s3_bucket_cors_configuration" "files" {
  bucket = aws_s3_bucket.files.id
  cors_rule {
    allowed_methods = ["PUT", "GET"]
    allowed_origins = concat([local.web_url], var.allowed_origins)
    allowed_headers = ["*"]
    expose_headers  = ["ETag"]
    max_age_seconds = 3000
  }
}
```

- The **lifecycle rule** throws away parts of big uploads that were never finished, after a day. Those parts are invisible in the bucket but still billed.
- **CORS** (<Term t="CORS">Cross-Origin Resource Sharing: a browser safety rule. JavaScript on one website may only call another address if that address says the website is allowed.</Term>) lets JavaScript on your web app's address PUT and GET files here. Without it the browser would block the upload before it starts. The bucket is still private: each request also needs a valid presigned URL.

The bucket also has `force_destroy = true`, so `terraform destroy` can delete it even when it still holds files.

**The files table (`dynamodb.tf`)** is one DynamoDB table with the key `file_id`, billed per request (`PAY_PER_REQUEST`). It holds several kinds of item side by side: a file uses its UUID as the key, a short link uses `QR#<code>`, a storage counter uses `USAGE#<user_id>`.

```hcl title="terraform/dynamodb.tf"
  global_secondary_index {
    name            = "user-files"
    hash_key        = "user_id"
    range_key       = "uploaded_at"
    projection_type = "ALL"
  }

  global_secondary_index {
    name            = "file-links"
    hash_key        = "target_file_id"
    range_key       = "created_at"
    projection_type = "ALL"
  }

  ttl {
    attribute_name = "ttl"
    enabled        = true
  }

  stream_enabled   = true
  stream_view_type = "OLD_IMAGE"
```

- A <Term t="global secondary index">A second way to look items up in a DynamoDB table, by a different attribute than the main key. DynamoDB keeps it up to date for you.</Term> lets you query by something other than `file_id`. `user-files` answers "all of Asha's files, newest first". It is **sparse**: only file items have a `user_id`, so links and counters never appear in it. `file-links` answers "all links to this file" the same way.
- **TTL** deletes any item whose `ttl` timestamp has passed. Unfinished uploads and expired links use it.
- The **stream** is a log of every change to the table. `OLD_IMAGE` means each deletion carries a copy of the deleted item, which the cleanup Lambda needs to know what to remove from S3.

The second table, `users` (in `auth.tf`), is simpler: one item per account, keyed by email.

</Step>

<Step number={5} title="The functions: lambda.tf and layers.tf">

One resource block creates all seven Lambdas from the `functions` map, using `for_each`:

```hcl title="terraform/lambda.tf"
data "archive_file" "fn" {
  for_each    = local.functions
  type        = "zip"
  source_dir  = "${path.module}/../endpoints/${each.value.dir}/src"
  output_path = "${path.module}/build/functions/${each.key}.zip"
  excludes    = ["**/__pycache__/**"]
}

resource "aws_lambda_function" "fn" {
  for_each = local.functions

  function_name    = "${local.prefix}-${each.key}"
  filename         = data.archive_file.fn[each.key].output_path
  source_code_hash = data.archive_file.fn[each.key].output_base64sha256
  handler          = "${each.value.module}.lambda_handler"
  runtime          = var.lambda_runtime
  role             = aws_iam_role.lambda.arn
  timeout          = 30
  memory_size      = 256
  ...
}
```

`archive_file` zips each function's `src/` folder. `source_code_hash` is a fingerprint of that zip: when the code changes, the fingerprint changes and Terraform uploads the new version. Every function also gets a CloudWatch log group that keeps logs for 14 days. The auth, authorizer and links functions are defined the same way in their own files.

**Layers.** Shared code is zipped straight from `endpoints/common`. The `jsonschema` library is different: it contains compiled parts, so it must be the Linux version, even if you deploy from Windows or a Mac. Terraform can't run pip, so a `null_resource` runs `build.sh` during `terraform apply`:

```hcl title="terraform/layers.tf"
resource "null_resource" "layers_build" {
  ...
  provisioner "local-exec" {
    interpreter = [var.bash_bin, "-c"]
    command     = "PYTHON='${var.python_bin}' PY_VERSION='${replace(var.lambda_runtime, "python", "")}' bash '${path.module}/build.sh'"
  }
}
```

`build.sh` asks pip for `manylinux2014_x86_64` wheels for Python 3.13, which is what runs on Lambda. This is the reason for the two Windows settings you will add in Step 16: Terraform needs to know where bash (`bash_bin`) and Python (`python_bin`) are.

</Step>

<Step number={6} title="The front door: API Gateway and the authorizer">

**`apigateway.tf`** creates a REST API and its URL tree: `/v1/users/{user_id}/files/{file_id}/complete`, `/download`, `/share`, `/parts`. Each route is wired up by a small reusable module, `modules/api-lambda-route`, which creates three things: the method (like `POST`), the integration (call this Lambda) and a permission that lets API Gateway invoke the function.

```hcl title="terraform/modules/api-lambda-route/main.tf"
resource "aws_api_gateway_method" "this" {
  rest_api_id      = var.rest_api_id
  resource_id      = var.resource_id
  http_method      = var.http_method
  authorization    = var.authorizer_id == null ? "NONE" : "CUSTOM"
  authorizer_id    = var.authorizer_id
  api_key_required = false
}

resource "aws_api_gateway_integration" "this" {
  ...
  integration_http_method = "POST"
  type                    = "AWS_PROXY"
  uri                     = var.lambda_invoke_arn
}
```

`AWS_PROXY` means a **Lambda proxy integration**: API Gateway hands the whole HTTP request to the function as one `event`, and sends back whatever status, headers and body the function returns. Routes passed an `authorizer_id` are protected; the rest (sign-up, sign-in and the public `/v1/d/{code}`) are open.

A second module, `modules/cors-options`, answers the browser's `OPTIONS` "preflight" request on every route the web app calls. Browsers send one before any request that carries an `Authorization` header.

The file ends with the stage (`dev`) and stage-wide throttling: 50 requests a second with bursts of 100. Anything over gets `429 Too Many Requests`, which caps password guessing and runaway costs.

**`authorizer.tf`** puts a <Term t="Lambda authorizer">A small Lambda that API Gateway runs before your route. It looks at the request (here, the token) and answers allow or deny. API Gateway can cache the answer.</Term> in front of every protected route:

```hcl title="terraform/authorizer.tf"
resource "aws_api_gateway_authorizer" "token" {
  name                             = "${local.prefix}-token"
  rest_api_id                      = aws_api_gateway_rest_api.api.id
  type                             = "TOKEN"
  authorizer_uri                   = aws_lambda_function.authorizer.invoke_arn
  identity_source                  = "method.request.header.Authorization"
  identity_validation_expression   = "^Bearer [-0-9A-Za-z._~+/=]+$"
  authorizer_result_ttl_in_seconds = var.authorizer_cache_seconds
}
```

The validation expression lets API Gateway reject a missing or malformed header without even running the Lambda. The cache (300 seconds by default) means a busy user's token is checked once every 5 minutes, not on every click. The same file adds CORS headers to API Gateway's own error answers, so the web app can actually see a 401 and renew its session.

**`auth.tf`** creates the users table, a random 48-character secret that signs tokens, the auth Lambda (with 1024 MB of memory, because password hashing is CPU-heavy and Lambda gives more CPU with more memory), and the public routes `/v1/users`, `/v1/login`, `/v1/userinfo`, `/v1/logout` and `/v1/refresh-token`.

**`qr.tf`** creates the links Lambda and its routes: the owner's `.../qr` and `.../links` routes (protected) and the public `GET` and `POST /v1/d/{code}`.

</Step>

<Step number={7} title="Permissions and email: iam.tf and ses.tf">

Every Lambda needs an IAM role: the permissions it runs with. The app's functions share one role, and each permission names exactly which resource it applies to:

```hcl title="terraform/iam.tf"
    {
      Effect = "Allow"
      Action = [
        "s3:PutObject", "s3:GetObject", "s3:DeleteObject",
        "s3:AbortMultipartUpload", "s3:ListMultipartUploadParts" # multipart uploads
      ]
      Resource = "${aws_s3_bucket.files.arn}/*"
    },
    ...
    {
      Effect   = "Allow"
      Action   = ["ses:SendEmail", "ses:SendRawEmail"]
      Resource = "*"
      Condition = {
        "ForAllValues:StringEquals" = { "ses:FromAddress" = var.sender_email }
      }
    }
```

This is **least privilege**: the functions can touch this app's bucket, this app's table and its stream, and can send email only *from* your sender address. Notice there is no `dynamodb:Scan`: the file functions always look items up by key or index. A presigned URL carries the permissions of whoever signed it, so these S3 permissions are also what makes the browser's presigned uploads and downloads work.

**`ses.tf`** registers `sender_email` as an SES identity. AWS then emails that address a verification link, and nothing is sent until you click it (Step 18).

</Step>

<Step number={8} title="Cleanup and hosting: cleanup.tf and web.tf">

**`cleanup.tf`** connects the table's stream to the cleanup Lambda with an <Term t="event source mapping">A Lambda setting that reads from a stream or queue for you and calls your function with batches of records.</Term>:

```hcl title="terraform/cleanup.tf"
resource "aws_lambda_event_source_mapping" "cleanup" {
  event_source_arn                   = aws_dynamodb_table.files.stream_arn
  function_name                      = aws_lambda_function.fn["cleanup"].arn
  starting_position                  = "LATEST"
  batch_size                         = 25
  maximum_batching_window_in_seconds = 60
  maximum_retry_attempts             = 3
  bisect_batch_on_function_error     = true

  filter_criteria {
    filter {
      pattern = jsonencode({
        eventName    = ["REMOVE"]
        userIdentity = { type = ["Service"], principalId = ["dynamodb.amazonaws.com"] }
        dynamodb     = { OldImage = { status = { S = ["UPLOADING"] } } }
      })
    }
  }
}
```

The filter is the clever part. The stream sees every write to the table, but the Lambda only runs for deletions made by DynamoDB itself (that is what TTL deletions look like) of records still marked `UPLOADING`. A normal delete or a finished upload never wakes it.

**`web.tf`** hosts the React app. The default, `web_hosting = "amplify"`, creates an Amplify app with a `main` branch and a rewrite rule that serves `index.html` for any path without a file extension, so React Router can handle `/login` or `/admin`. The other option, `"cloudfront"`, creates a private S3 bucket behind CloudFront.

<Callout type="info" title="Why Amplify is the default">

Brand-new AWS accounts can't create CloudFront distributions until AWS Support has verified the account. Amplify Hosting works straight away, so it is the safe default. You can switch later and redeploy.

</Callout>

</Step>

<Step number={9} title="Extra credit files (skim these)">

These add the grown-up features. You can deploy and use DropVault without understanding them.

- **`monitoring.tf`**: an SNS topic `enclave-dev-alerts` that emails `alert_email`; a CloudWatch alarm for each Lambda's errors (all but the authorizer, which "fails" on every rejected token) plus API 5xx and a 4xx spike; a log subscription that sends every `ERROR` line to a monitor Lambda; and an EventBridge schedule that runs the monitor's health check every `health_check_minutes` (5).
- **`admin.tf`**: the admin Lambda behind `ANY /v1/admin/{proxy+}`, with its own IAM role. It is the only function allowed to scan whole tables and read CloudWatch.
- **`kms.tf`**: the optional KMS key for `kms_mode = "shared"`, and a destroy-time script that removes per-user keys created at runtime.
- **`domain.tf`**: an optional custom domain for the API (`api_domain_name`), with its own HTTPS certificate.
- **`outputs.tf`**: values Terraform prints after `apply`, like `api_url` and `web_url`. `deploy.sh` reads them.

## Part 3: The Lambda functions

All handlers are short, because the shared layer does the repetitive work.

<Step number={10} title="The shared layer: endpoints/common/python">

Most file handlers are wrapped in a decorator from `api.py`. The handler just returns `(status, body)` or raises `ApiError`, and the decorator turns that into a proper API Gateway response with CORS headers. A crash becomes a logged error and a clean `500`.

```python title="endpoints/common/python/api.py"
def require_user(event):
    '''(user_id, name, email) of the caller, whose id must match the path.'''
    user_id, name, email = auth.resolve_event_user(event)
    if not user_id:
        raise ApiError(401, 'Unauthorized')
    if auth.path_param(event, 'user_id', 3) != user_id:
        raise ApiError(403, 'User not authorized to perform this action')
    return user_id, name, email
```

This check matters. The authorizer proves *who you are*; `require_user` makes sure the `{user_id}` in the URL is *you*, so nobody can list someone else's files by editing the address. `owned_file` goes one step further and checks the file in the path belongs to you.

Other helpers you will see everywhere:

- `storage.object_key(item)` builds the S3 key `{user_id}/{file_id}/{file_name}`. Two people can upload `notes.pdf` without clashing.
- `storage.presign_s3()` signs URLs against the regional S3 address (`s3.ap-south-1.amazonaws.com`), because the global address can answer with a redirect that breaks browser uploads.
- `links.py` creates and checks short links, `usage.py` keeps the storage quota, `tokens.py` signs and verifies tokens.

</Step>

<Step number={11} title="Signing in: auth-service and authorizer">

**`auth-service/src/auth_service.py`** (one Lambda, five routes, chosen by method and path):

| Receives | Does | Returns |
| --- | --- | --- |
| `POST /v1/users` with `full_name`, `email`, `password` | checks the input, hashes the password (PBKDF2-SHA256, 200,000 rounds), saves the user only if the email is new | `201` with tokens, `user_id`, `role` (or `409` if the email exists) |
| `POST /v1/login` with `email`, `password` | compares the hash; hashes a dummy value for unknown emails so both cases take the same time | `200` tokens, `401`, or `403` if suspended |
| `POST /v1/refresh-token` | checks the refresh token and that the session is still valid | new tokens |
| `POST /v1/logout` | adds 1 to the account's `token_version` | `200`, and every old token stops working |

A token is two parts joined by a dot: base64 JSON claims (`sub`, `email`, `name`, `ver`, `typ`, `exp`) and an HMAC-SHA256 signature made with the secret from `auth.tf`. Anyone can read the claims, but nobody can change them without breaking the signature. Because the expiry is inside the token, the server keeps no session list. ID and access tokens last 1 hour, refresh tokens 30 days.

**`authorizer/src/authorizer.py`** receives the `Authorization` header from API Gateway. It verifies the signature and expiry, then reads the account from the users table: it must still exist, not be suspended, and its `token_version` must equal the token's `ver`. If all is well it returns an "Allow" policy for the whole API plus `context: {user_id, name, email}`, which reaches every file Lambda as `requestContext.authorizer`. Otherwise it raises exactly `Exception('Unauthorized')`, which API Gateway turns into a 401.

The policy covers the whole API (not just this one route) on purpose: API Gateway caches it per token and reuses it for every route that token calls.

</Step>

<Step number={12} title="Uploading: upload-file and complete-upload">

**`upload-file/src/upload_file.py`** handles two routes.

`POST /v1/users/{user_id}/files` receives `{file_name, content_type, size}`. It checks the body against `schemas/new_file.json` (a name with no slashes, up to 255 characters), refuses early with `413` if the file obviously won't fit your quota, and creates a record with `status: "UPLOADING"` and a `ttl` one day out. Then:

- **Up to 100 MB:** it returns `upload_type: "single"` and one presigned PUT URL, valid for 1 hour.
- **Over 100 MB:** it starts an S3 multipart upload and returns `upload_type: "multipart"`, a `part_size` (at least 16 MB, and big enough to stay within S3's 10,000-part limit) and a `part_count`.

`POST .../{file_id}/parts` receives `{part_numbers: [1, 2, ...]}` and returns a presigned URL for each part (up to 100 at a time). With `include_uploaded: true` it also lists the parts S3 already has, which is how a paused upload resumes after a page reload. Every call pushes the record's `ttl` another day ahead, so an upload that is still moving is never cleaned up.

**`complete-upload/src/complete_upload.py`** receives `POST .../{file_id}/complete` once the bytes are in S3. For a multipart upload it lists the parts and asks S3 to stitch them together (`409` with `missing_parts` if some are missing). Then it asks S3 for the real size, adds it to your usage counter, and marks the file `READY`, removing the `ttl`:

```python title="endpoints/complete-upload/src/complete_upload.py"
    try:
        usage.add(user_id, size)
    except usage.QuotaExceeded:
        discard(item)
        raise api.ApiError(413, 'Not enough storage space for this file',
                           used_bytes=usage.used_bytes(user_id), quota_bytes=usage.quota_bytes(user_id)) from None
```

`usage.add` is one conditional DynamoDB update (`used_bytes <= :limit`), so two uploads finishing at the same moment can't both squeeze past the 10 GB limit. It uses the size S3 actually stored, not the size the browser claimed.

</Step>

<Step number={13} title="Listing, downloading and deleting">

- **`get-user-files`**: `GET /v1/users/{user_id}/files` queries the `user-files` index (no table scan) and returns `{user_id, user_files: [...], usage: {used_bytes, quota_bytes}}`. Unfinished multipart uploads are marked `resumable`.
- **`download-file`**: `GET .../{file_id}/download` returns `{file_id, file_name, download_url}`, a presigned GET valid for 1 hour, for your own READY file. The URL sets `Content-Disposition` so the browser saves it under the original name.
- **`delete-user-file`**: `DELETE .../{file_id}` aborts the multipart upload if there is one, deletes the S3 object and the record, subtracts the size from your usage, and deletes the file's short links. It returns `{file_status: "DELETED"}`. Deleting with `ReturnValues='ALL_OLD'` tells it whether *this* call really removed the file, so two parallel deletes can't subtract the size twice.

</Step>

<Step number={14} title="Sharing: share-file and qr-link">

**`share-file/src/share_file.py`** receives `{share_with: [emails], expires_in, max_downloads}` (1 to 10 unique addresses). For each recipient it creates a short link with `channel: "email"`, then sends an HTML email through SES. Everything the user typed (their name, the file name) is HTML-escaped, so nobody can inject links into mail sent from your verified address. One failed email doesn't stop the others: its link is deleted and the address is listed under `failed` with a reason. The SES sandbox case gets a friendly message suggesting Copy link instead.

**`qr-link/src/qr_link.py`** has owner routes and public routes:

| Route | What it does |
| --- | --- |
| `POST .../qr` `{expires_in, max_downloads, channel}` | creates a short link, returns `{short_url, expires_at, max_downloads}` |
| `GET .../links` | every link for the file, with `downloads`, `last_downloaded_at` and a `status` |
| `DELETE .../links/{code}` | turns one link off (sets `revoked_at`) |
| `DELETE .../qr` | turns off every link made so far (stamps `links_revoked_at` on the file) |
| `GET /v1/d/{code}` (public) | checks the link, then redirects to a fresh 5-minute download, or shows a Download button page for limited links |
| `POST /v1/d/{code}` (public) | the Download button: counts one download, then redirects |

`expires_in` must be `900`, `3600`, `21600`, `86400`, `604800` (15 minutes to 7 days) or `"never"`, and defaults to 1 hour. `max_downloads` is 1 to 1000, or `null` for unlimited.

Every visit to `/v1/d/{code}` runs the same checks in order: does the file still exist and is it READY (else `404`), was the link turned off, has it expired, is the download limit used up (each `410` with a readable page). Then `record_download` counts the download with a conditional update (`downloads < :max`), so two people can never both take the last download. Finally the visitor is redirected to a presigned GET that lives 5 minutes.

<Callout type="info" title="Why a button for limited links?">

Email security scanners and chat apps open links on their own to build previews. If a plain GET counted as a download, a one-time link could be used up before your friend even saw it. A GET only shows the page; the Download button sends a POST, which counts.

</Callout>

</Step>

<Step number={15} title="Cleaning up: cleanup">

**`cleanup/src/cleanup.py`** receives batches of stream records (at most 25, filtered by `cleanup.tf`). For each one it checks again that it is a `REMOVE` made by `dynamodb.amazonaws.com` of an `UPLOADING` item, rebuilds the old item from DynamoDB's typed JSON (`{"S": "UPLOADING"}`) with `TypeDeserializer`, and then:

```python title="endpoints/cleanup/src/cleanup.py"
def clean(item):
    s3 = storage.s3()
    key = storage.object_key(item)
    if item.get('upload_id'):
        try:
            s3.abort_multipart_upload(Bucket=storage.bucket(), Key=key, UploadId=item['upload_id'])
        except ClientError as error:
            if error.response.get('Error', {}).get('Code') != 'NoSuchUpload':
                raise
    s3.delete_object(Bucket=storage.bucket(), Key=key)   # no error if it isn't there
```

It returns `{"cleaned": n}`. Ignoring `NoSuchUpload` makes it safe to run twice: if the S3 lifecycle rule already aborted the upload, there is nothing to do.

</Step>

## Part 8: Challenges

<Step number={24} title="Make it your own">

Pick one. Each is a real feature request, small enough for a weekend, and touches a different AWS idea.

- **Password-protected links.** Add an optional password when creating a link, store a PBKDF2 hash on the link item (reuse `accounts.hash_password`), add a password box to the Download page, and check it in `follow_link` before `record_download`.
- **"Your file was downloaded" emails.** In `record_download`, when `first_downloaded_at` is set for the first time, email the owner with SES. Think about where the owner's email comes from (hint: `owner_id`, and the users table is keyed by email).
- **Custom domain for the web app.** The one unticked item on the README roadmap. Amplify Hosting supports custom domains; `domain.tf` already shows how the API gets one with its own certificate.
- **Limit sign-in attempts.** The README says there is no rate limiting on login. Count failed attempts per email in the users table, with a TTL so the counter resets, and refuse with `429` after five.
- **Image thumbnails.** Add an S3 event notification that runs a new Lambda when an image arrives, and save a small preview next to it.
- **Remote Terraform state.** Move `terraform.tfstate` into an S3 bucket with a `backend "s3"` block, as the comment in `versions.tf` suggests, so a teammate can deploy too.
- **Write a test first.** The repo has a pytest suite that runs the real handlers against a fake AWS (moto). Run `pytest`, then add a test for your new feature before you build it.

Run `bash deploy.sh` after each change: Terraform updates only what changed.

</Step>
